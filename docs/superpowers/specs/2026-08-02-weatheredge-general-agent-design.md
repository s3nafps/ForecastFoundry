# WeatherEdge General Quantitative Agent

## Change request

This specification expands the approved weather-only milestone into a general, standalone Polymarket quantitative engine with crypto as the first additional domain and optional Hermes Agent integration.

- **ADDED:** domain-plugin routing, crypto price/threshold markets, public crypto data providers, optional keyed weather providers, encrypted wallet execution, balanced autonomous risk controls, and a local Hermes MCP server.
- **MODIFIED:** WeatherEdge changes from permanently paper-only to an explicit execution mode. Paper mode remains the default; live execution requires a separate opt-in flag and all controls below.
- **UNCHANGED:** deterministic rule parsing, source provenance, exact resolution matching, UTC storage, rejection of ambiguous markets, and the existing weather flow.

## Goals

1. Run standalone on a Linux VPS with Docker Compose.
2. Run the same engine with or without Hermes Agent.
3. Support daily maximum-temperature markets and BTC/ETH price-threshold markets first.
4. Use authoritative resolution sources and preserve every data/model decision for audit.
5. Permit autonomous execution only through an isolated encrypted-keystore signer and shared risk engine.
6. Add providers without changing the prediction or execution core.

## Non-goals for this milestone

- Sports, elections, economics, rainfall, snow, and hurricane plugins are not implemented in this milestone.
- X, Reddit, and GitHub content is not authoritative resolution data and cannot directly authorize an order.
- Hermes never receives a wallet key, signs raw orders, changes risk limits, or calls an arbitrary network endpoint.
- There is no leverage, borrowing, martingale sizing, averaging down, or wallet transfer automation.

## Architecture

```text
Polymarket discovery and rules
             |
      domain plugin router
       /                 \
 weather plugin       crypto plugin
       \                 /
        normalized evidence contract
                    |
        source data + deterministic models
                    |
          probabilities and uncertainty
                    |
            shared signal/risk engine
                    |
          isolated wallet execution service
                    |
             ledger and reconciliation

Hermes Agent -- local stdio MCP --> research/status/control tools
```

The scheduler, database, API, dashboard, provider registry, model engine, risk engine, and executor are useful without Hermes. Hermes is a client of the system, not its owner.

## Domain contract

Every plugin implements a validated protocol equivalent to:

```python
class DomainPlugin(Protocol):
    domain: str

    def recognize(self, market: GammaMarket, event: GammaEvent) -> bool: ...
    def normalize(self, market: GammaMarket, event: GammaEvent) -> NormalizedContract: ...
    async def collect(self, contract: NormalizedContract) -> EvidenceBundle: ...
    def estimate(self, contract: NormalizedContract, evidence: EvidenceBundle) -> Prediction: ...
```

`NormalizedContract` must include the exact resolution source, target, units, comparison, threshold/bucket, timestamp, timezone, and any rounding rule. Missing or ambiguous fields produce a stored `unsupported_domain` or `ambiguous_rules` rejection.

`EvidenceBundle` records provider name/version, request time, source timestamp, raw response hash, normalized values, freshness, license/attribution metadata, and quality flags. Predictions record model name/version, feature snapshot, valid sample count, probability, uncertainty, and calibration metrics.

## Weather plugin

The existing daily maximum-temperature flow remains the first production plugin. It continues to use Open-Meteo ensemble members, audited stations, explicit rule provenance, local-day timezone handling, exact bucket mapping, and rejection of incomplete markets.

The provider registry additionally supports:

- keyless official sources: Open-Meteo, NWS, AviationWeather, and MET Norway;
- optional user-supplied keyed sources: WeatherAPI, Visual Crossing, Tomorrow.io, and OpenWeather.

Free tiers are quotas and licenses, not unlimited keys. Keys are never discovered or generated by the application. Users place their own credentials in Docker secrets. The registry records quota, attribution, rate limit, and whether a provider is authoritative, corroborating, or feature-only.

## Crypto plugin

The first crypto markets are BTC and ETH threshold/up-down markets only.

Normalization requires:

- asset and quote currency;
- exact exchange, index, or oracle named by the rules;
- threshold and comparison direction;
- exact resolution timestamp and timezone;
- candle/price definition and rounding;
- close/expiry behavior.

The plugin rejects generic or conflicting questions such as “Bitcoin price” without a deterministic source and timestamp.

Initial public data providers are Coinbase Exchange, Binance public market data, and Kraken. Chainlink or another oracle is used only when the market names it as the resolution source. Cross-provider prices are quality checks; they never replace the stated resolution source.

The first deterministic crypto estimator uses:

1. matched-source historical log returns at the market horizon;
2. empirical bootstrap quantiles;
3. EWMA volatility with drift shrunk toward zero;
4. a volatility-based Monte Carlo distribution;
5. equal model weighting until walk-forward calibration demonstrates a better fixed weighting.

A model requires a configurable minimum history and freshness window. If data is insufficient, stale, internally inconsistent, or unavailable at the resolution source, no probability or signal is produced. Sentiment or narrative features from X/Reddit are stored separately and cannot affect live probability until a versioned walk-forward test beats the non-social baseline.

## Shared prediction and signal rules

For every domain:

```text
raw_edge = calibrated_probability - executable_best_ask
usable_edge = raw_edge - fees - slippage - uncertainty - rule_risk
```

Signals require active market state, complete rules, fresh authoritative evidence, minimum quality, available executable ask, acceptable spread/liquidity, sufficient data, and positive usable edge. Every rejection stores every failed gate and the complete candidate snapshot.

Market-implied probability is a benchmark, not independent evidence. The system reports calibration, Brier score, log loss, and out-of-sample performance separately from simulated or live P&L.

## Autonomous risk and wallet execution

The selected balanced profile is fixed in configuration:

- maximum 5% of available equity per position;
- maximum 25% aggregate open exposure;
- maximum 10% realized/unrealized daily loss;
- no leverage and no automatic transfers;
- correlated crypto positions share an asset exposure bucket.

Position sizing is fractional Kelly using the uncertainty-adjusted probability, capped by the above limits and reduced by existing exposure, open orders, fees, minimum size, and available balance. A signal can be mathematically positive and still be rejected by the risk engine.

The executor performs this sequence for every opening order:

1. verify geoblock and account closed-only status;
2. verify wallet balance, allowance, key permissions, and current risk limits;
3. fetch fresh market rules, tick size, minimum size, and order book;
4. recompute probability, edge, and size from the same point-in-time snapshot;
5. create a bounded marketable limit order, never an unbounded market order;
6. sign locally inside the executor process;
7. submit through the official Polymarket Python SDK;
8. fetch order state and account trades;
9. reconcile partial fills, cancel stale remainder, and persist all IDs/statuses;
10. pause new entries on unknown status, provider disagreement, or risk-limit breach.

The encrypted keystore is stored on the Linux VPS as a Docker secret or root-readable file with strict permissions. The unlock password is injected only into the executor process at startup. The MCP process, API responses, logs, and Hermes context never contain key material.

Paper mode remains the default. Live mode requires both `EXECUTION_ENABLED=true` and an explicit deployment confirmation value, and startup fails if caps are absent, invalid, or greater than the balanced profile.

## Provider and community research

The registry has four evidence classes:

1. authoritative resolution data;
2. official/maintained SDK and API implementation data;
3. operational research from X, Reddit, GitHub issues, changelogs, and outages;
4. model-derived features.

Community content is timestamped, URL-hashed, sanitized, and rate-limited. It can generate an investigation record or provider-health alert, but cannot change rules, install code, alter limits, or place an order. X and Reddit integrations are optional and require the user’s own credentials and compliance with their current terms.

## Hermes MCP

The local stdio MCP server exposes only:

- `list_supported_domains`;
- `scan_markets`;
- `get_market_evidence`;
- `explain_prediction`;
- `run_backtest`;
- `provider_health`;
- `portfolio_status`;
- `reconcile_orders`;
- `pause_execution`;
- `resume_execution`.

The tool allowlist disables prompts/resources and parallel calls. There are no `place_order`, `sign_order`, `set_risk_limits`, `wallet_transfer`, or arbitrary HTTP tools. Pause/resume requests are authenticated, audited, and still subject to the local execution policy.

## Persistence additions

Add tables for:

- `domain_contracts` and normalized resolution fields;
- `provider_registry` and provider health/quota state;
- `evidence_snapshots` with raw-response hashes;
- `prediction_runs`, feature snapshots, calibration metrics, and model versions;
- `execution_orders`, fills, reconciliation events, and kill-switch events;
- `research_documents` for X/Reddit/GitHub evidence;
- encrypted-keystore metadata only (never the key or password).

Existing weather, signal, paper, and error tables remain compatible. Live execution adds separate order/fill records rather than overloading paper positions.

## Deployment and safety

The first target is a single Linux VPS running Docker Compose with a named `/data` volume, a non-root application user, encrypted secrets, loopback-only HTTP binding, and an optional Nginx TLS proxy. The executor and MCP server run as separate processes or containers with the executor’s secret mount absent from the MCP container.

Startup is fail-closed when configuration, keystore permissions, geoblock, database migrations, provider registry, or risk caps are invalid. Emergency shutdown cancels all known open orders, disables new entries, and records the reason.

## Acceptance evidence

Before live mode is enabled:

- unit tests cover crypto timestamp/threshold parsing, return aggregation, bootstrap/Monte Carlo determinism, calibration, sizing, caps, and order reconciliation;
- recorded fixtures cover weather and crypto markets;
- paper walk-forward results meet configured calibration thresholds;
- a testnet or mocked SDK verifies signing and order-state handling without real funds;
- Hermes MCP tool filtering is tested to prove no signer/key tool is exposed;
- provider failure, stale source, geoblock, closed-only, partial fill, unknown status, and daily-loss stops are tested;
- a live deployment requires an explicit operator review of the current Polymarket terms, jurisdiction, and account permissions.
